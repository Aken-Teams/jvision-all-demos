# 部署與資安待處理

> 盤點日期 2026-09-03。每一項都附了檔案與行號，可以逐項打開對照。
> 排序依「不修的後果」而不是「修起來多快」。

實例交付目前有三條路，這份文件講的是第三條：

| 路徑 | 誰託管 | 網址 | 誰看得到 |
|---|---|---|---|
| 平台上 | 我們 | `/-/i/<id>/`、`c-xxx.jvision-ai.com` | Google 登入 ＋ 該公司白名單 |
| GitHub repo | 客戶自己 | 他自己架 | 他決定 |
| **Vercel** | Vercel | **公開網址** | **任何拿到連結的人** |

前兩條沒有下列問題。

---

## 1. 公開部署的憑證可以觸及整個平台

**嚴重度：最高。這是唯一一項「單點失守會波及所有客戶」的。**

`tools/instance-deploy-vercel.mjs:167-171` 在部署時設定環境變數：

```js
["MYSQL_HOST", env("MYSQL_HOST")], ["MYSQL_PORT", env("MYSQL_PORT")],
["MYSQL_USER", env("MYSQL_USER")], ["MYSQL_PASSWORD", env("MYSQL_PASSWORD")],
["MYSQL_DB", pubDb],
```

帳號密碼是從 `.env` **原封不動**送過去的，只有「預設資料庫」被縮小到 `<實例>_pub`。

問題在於 **MySQL 的權限綁在帳號上，不是綁在預設資料庫上**。同一個帳號連進去之後
`USE` 別的資料庫是擋不住的。而且那組帳號確定權限很大——部署流程自己會呼叫
`createDatabase()` 建立 `_pub` 資料庫，也就是它有 `CREATE DATABASE`。

實際核對過資料庫的使用者清單，非系統帳號只有 `A999@%` 與 `aken@%`，
而 `.env` 裡 `MYSQL_*`（許願池）與 `JV_MYSQL_*`（控制面＋所有實例）**用的都是 A999**。
沒有任何分權。

**結論**：現在有一個公開、無身分驗證的 Vercel 應用，持有可以讀寫
`jv_demo_case`（客戶、成員、訂單、對話）與每一個 `jv_<實例>` 的憑證。

### 怎麼修

建一個部署專用的 MySQL 帳號，只授權它自己那個 `_pub` 資料庫：

```sql
CREATE USER 'jv_pub'@'%' IDENTIFIED BY '<夠長的隨機密碼>';
-- 每次部署新實例時追加一行；或授權整個 jv_%_pub 樣式
GRANT SELECT, INSERT, UPDATE, DELETE ON `jv_<實例編號>_pub`.* TO 'jv_pub'@'%';
```

然後在 `.env` 加 `PUB_MYSQL_USER` / `PUB_MYSQL_PASSWORD`，把
`instance-deploy-vercel.mjs` 那五行改成讀這一組。

**成本**：約半小時，零應用程式邏輯改動。
**擋掉的**：把「平台級外洩」降成「單一 demo 外洩」。

## 2. 公開網址可以刪光資料，沒有任何身分驗證

`tools/lib/nextjs-bundle.mjs` 產生的 API：

| 端點 | 行號 | 作用 |
|---|---|---|
| `GET /api/t/<表>` | 198 | 讀任何一張表 |
| `POST /api/t/<表>` | 212 | 新增 |
| `PATCH /api/t/<表>/<id>` | 230 | 修改 |
| `DELETE /api/t/<表>/<id>` | 245 | 刪除 |

四個都沒有身分檢查，也沒有限流——整份檔案裡沒有出現過 `authorization`。
任何人拿到那個網址，就能把整套系統的資料刪光；而那是客戶要拿去給人看的東西。

### 怎麼修（兩選一）

- **公開版唯讀**：`nextjs-bundle.mjs` 不產生 `POST`/`PATCH`/`DELETE` 三個 handler。
  要給人看的 demo，多半不需要對方能寫。
- **寫入端加 token**：部署時產生一組，寫進環境變數，前端帶在標頭上。
  能寫但只有拿到連結＋token 的人能寫。

另外建議加上限流，避免有人反覆呼叫把資料庫打滿。

---

## 3. 公開的是真實資料的複本

`tools/instance-deploy-vercel.mjs` 的註解寫著：

> 部署版用自己的一份資料庫（`jv_<實例編號>_pub`），從實例現況複製過去：
> 公開的那份完全能用，但碰不到客戶真正的資料。

這句話**只保護了寫入方向**。`mirrorDatabase()` 是用 `CREATE TABLE LIKE` ＋
`INSERT SELECT` 整份複製，所以**內容就是客戶的真實業務資料**（名單、訂單、報價），
只是放在另一個 schema。公開讀取等於資料揭露。

### 怎麼修

在按下部署之前，明確告訴客戶「這會把目前的資料複製到一個公開網址」，
並提供「只帶結構不帶資料」的選項（`CREATE TABLE LIKE` 之後不做 `INSERT SELECT`）。

這是產品決定，不只是技術決定——要先確認客戶預期的是「給人看畫面」還是
「給人看畫面＋真資料」。

---

## 4. 所有資料庫住在同一台伺服器

```
sharemysql.theaken.com
├── db_Survey            許願池（MYSQL_*）
├── jv_demo_case         控制面：客戶、成員、訂單、實例、對話
└── jv_<實例編號> × N     每個客戶的業務資料
```

加上第 1 項，等於「公開應用的憑證」與「公司其他重要資料」在同一台機器上。

### 搬遷成本（程式碼已經幫忙分好一半）

`.env` 本來就是兩組獨立變數，所以：

| 做什麼 | 要改什麼 |
|---|---|
| 許願池 `db_Survey` 搬走 | **只改 `MYSQL_HOST`**，程式碼零改動 |
| `JV_MYSQL_*` 整組搬到專用主機 | 改變數 ＋ 資料遷移，程式碼零改動 |
| 控制面與實例再拆成兩台 | 要改 `tools/lib/mysql.mjs`——它現在只有一個連線池 |

第三種是最徹底的隔離：客戶實例的憑證外洩也碰不到控制面。

---

## 建議順序

1. **第 1 項先做**。不是搬家、不用停機，只是換一組憑證，卻擋掉最嚴重的路徑。
2. 第 2 項跟著做，決定公開版要唯讀還是加 token。
3. 第 3 項是產品決定，要跟客戶對齊預期。
4. 第 4 項等部署架構定案時一起規劃。

## 附帶：`.env` 裡該輪替的憑證

以下曾出現在截圖中，建議直接換發：

- `VERCEL_TOKEN`
- `OLLAMA_API_KEY`
- `MYSQL_PASSWORD` / `JV_MYSQL_PASSWORD`（同一組 A999，現值只有四位數）

`.env` 不在版控裡，換完不需要改任何程式碼。
