# JVision All Demos — Decision Log

| Date | Decision | Rationale | Consequence |
| --- | --- | --- | --- |
| 2026-07-22 | Use one public JV Demo domain. | Visitors need one reliable entry point for all projects. | Hub links use `/demos/<repo>/`; do not expose old per-project Vercel URLs as the primary Demo action. |
| 2026-07-22 | Make the homepage retrieval-first rather than marketing-first. | The site is a company demo catalog, not a landing page. | Keep copy compact; prioritise search, facets, result count and direct Demo links. |
| 2026-07-22 | Keep every project independently runnable. | The monorepo must preserve project-level evaluation and development. | Do not collapse projects into static placeholders solely for Hub rendering. |
| 2026-07-22 | Use `projects-index.json` as Hub catalog source of truth. | Catalog data needs one auditable location. | Update it when a project's public route, repo or classification changes. |
| 2026-07-22 | Use a light, high-contrast professional SaaS baseline. | The product represents JV's AI-enabled SaaS capability and must remain clear on desktop and mobile. | Individual project style may vary, but contrast, responsive behaviour, forms and statistics views must meet the shared baseline. |
| 2026-07-22 | Keep Vercel production deployment out of the per-project workflow. | The target experience is one-domain hosting, not hundreds of separate deployments. | Validate locally/self-hosted and use the single-domain publishing path when release is required. |
| 2026-07-22 | Route catalog administration through GitHub pull requests. | The public site must not expose repository credentials or permit direct production writes. | Admin edits remain local drafts until an authenticated server action creates a feature branch and PR. |
| 2026-07-22 | Keep repository identity and migration provenance out of public catalog cards. | Visitors need to understand the product, not its source-control or legacy status. | Public cards show a project introduction and Demo action only; repository identifiers remain available inside administration and canonical data. |
| 2026-07-22 | Give every project one primary business category. | Combined labels such as education and care make discovery ambiguous. | Public classification uses a single domain such as education, healthcare, manufacturing or information security; implementation frameworks are not card metadata. |
| 2026-07-23 | Provide AI recommendations through one server-side DeepSeek endpoint. | The API key must never reach the browser and every Demo needs the same audited safety, timeout and rate-limit boundary. | Existing generated-system AI actions call `/api/ai-advice`; standalone legacy demos receive the same shared fallback trigger. |
| 2026-07-23 | Derive dynamic trend charts from each Demo's current operational statistics. | A shared runtime keeps visual quality and mobile accessibility consistent while allowing each system's own interactions and local records to drive the displayed result. | Every Demo exposes 7/30-day AI-score trends, a refresh action, a target line and an expandable data table without introducing an additional charting dependency. |
| 2026-07-23 | Use signed browser-scoped links for project sharing. | Recipients need a focused single-Demo share experience without making the public Demo catalog private. | A seven-day signed link sets an HttpOnly scope cookie; routing middleware permits only that Demo, its shared assets and required AI endpoint for the active browser session. This is navigation containment, not private-content authorization. |
| 2026-07-29 | Evaluate every Demo by its operational workflow, not by requiring a generic analytics panel. | A chart is not appropriate for every module and the customer needs credible domain actions. | Acceptance requires a domain workflow with stages and actions when an analytics panel is not applicable. |
| 2026-07-29 | Treat React #418 from preserved legacy Hub snapshots as a compatibility warning only after functional verification passes. | The old snapshots remain interactive but cannot currently be rebuilt cleanly with the Next.js 16 and legacy TypeScript combination. | HTTP, interaction, responsive and non-hydration browser errors remain blocking; the known recoverable warning is reported separately. |
| 2026-07-30 | Derive an explicit process-governance blueprint for every Demo. | A credible customer Demo must explain who acts, which data is required, when approval is needed and what operational result is produced. | Every workflow stage exposes an owner, inputs, action, pass/reject conditions and output; approval permissions and result documents use the same blueprint. |
| 2026-07-30 | Store each project's customer workflow in the canonical catalog. | Category-only templates made unrelated projects read and behave alike. | `projects-index.json` may include `customerWorkflow`; the shared showcase runtime uses it before a category fallback, while handcrafted showcases remain authoritative. |
| 2026-08-10 | Ground AI advice in structured on-screen evidence and role-specific tasks. | Generic page summaries cannot reliably explain which visible record or metric supports a recommendation. | AI requests include project, module, role, task and bounded evidence; responses cite that evidence, expose confidence and never apply consequential actions without human confirmation. |
| 2026-08-10 | Derive every Demo's guided entry from canonical project workflow metadata. | Visitors need to understand the problem, next three actions and expected result before navigating a dense product interface. | The shared client runtime renders a first-screen scenario entry from `businessSituation` and `customerWorkflow`; it launches the existing interactive workflow and does not replace the Demo's independent runtime. |

Add a row whenever a decision changes public routes, architecture, data ownership, design policy or deployment policy.

| 2026-08-22 | Keep `tools/demo-publish.mjs` as the only writer of `projects-index.json`. | Publishing is the one irreversible step in the generation pipeline and needs a single auditable entry point. | Build and verify never touch the catalog; publishing backs up the previous catalog and re-runs the structure and similarity audits. |
| 2026-08-22 | Have the codex CLI return Demo HTML as its final message instead of writing files. | Sandboxed codex cannot create files in this environment (`bwrap` loopback is blocked), and bypassing the sandbox to work around that is not acceptable. | `demo-forge` runs codex read-only and writes the file itself; a git diff allowlist reverts anything written outside `demos/<repo>/`, `content/details/<repo>.json` and the manifest. |
| 2026-08-22 | Generate `content/details/<repo>.json` and `README.md` from templates, leaving only `index.html` to the model. | The two data files have a fixed schema that a template satisfies every time, while the HTML is the part that needs domain judgement. | Schema conformance is guaranteed by construction and the model's output length drops, which materially lowers the failure rate. |
| 2026-08-22 | Repair responsive overflow by measurement rather than a shared stylesheet. | A single shared rule cannot fit 473 different layouts: an `!important` grid override collapsed the `.shell` rail and beat each Demo's own correct mobile rules, breaking 4 of 12 sampled Demos while fixing 4. | `tools/fix-demo-overflow.mjs` measures each Demo in a browser, emits CSS only for the elements that actually overflow, and re-measures before writing. |
| 2026-08-22 | Record usage as a salted visitor hash, never an IP address. | `AGENTS.md` forbids storing private network details, but the catalog owner still needs to know which Demos are actually opened. | The `npm run dev` gateway logs a per-start salted hash to gitignored `var/usage.jsonl`; visitor counts remain accurate while the records cannot be traced back to a machine. |
